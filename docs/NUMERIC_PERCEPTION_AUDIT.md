# Numeric perception audit — where the number goes wrong before the rail

Status: **investigation only — no code change, no new rule** (owner brief 2026-09-04).
Evidence: `session_20260904_133627` (build `b228048`, first live run of L1–L6), with
`session_20260903_103339`, `session_20260904_125037`, `session_20260904_131245` for the
STT statistics. Every table below is regenerated by
`python3 phase5/harness/numeric_audit.py` from the shipped code.

Fidelity check first: the offline chain (`precision_rail.decide` +
`value_transaction.mark_heard` with the log's heard/unheard outcomes) reproduces
**all 12 spoken lines of 133627 verbatim** (§1 of the script). Everything that follows
is therefore about the code path the user actually heard, not a model of it.

---

## 1. The question

> Why can this agent fail to reliably know/write the number even though L1–L6 now
> prevent unsafe mutation?

Short answer: **L1–L6 made the transaction safe; nothing in the chain makes the
observation safe.** The system has no representation of "what digit sequence was
heard, and how sure are we" — it has a *string* from whisper, a regex that slices a
span out of it, and a normalizer that throws away whatever it does not recognise.
Every downstream decision (append vs replace, edit vs dictation, confirm vs not) is
then made on properties of that string's *surface form* rather than on the digits.

The first missing boundary is **HEARD → UNDERSTOOD**: there is no numeric
observation object between STT and the rail. Details and proof below.

Three structural facts fall out of the table:

1. **The operation depends on the surface form, not the digits.** `125801203` and
   `1, 2, 5, 8, 0, 1, 2, 0, 3` are the same observation; one appends, the other
   replaces (`_is_full_restatement`: ≥8 separated digits = "re-spell"). Whisper
   chooses the surface form, so whisper is choosing the operation.
2. **Normalization is lossy and lexicon-gated.** An out-of-vocabulary digit word
   (`सिस`) does not produce "uncertain digit" — it deletes the whole observation and
   lets the *other* words in the sentence (a confirm word) decide. A count next to a
   digit (`5 जीरो`) is normalized as two digits (`50`).
3. **Composition is text concatenation.** L3 joins fragments and re-parses the string;
   a fragment's *reference* ("इसमें जो 5" = the 5 in the proposal you just read back)
   is resolved against the base, never against the proposal being discussed.

## 4. Is STT sufficient for digit-perfect recognition? — quantified

Ground truth audio is not retained (`AIVA_TTS_DUMP` saves *agent* audio only; user
audio is never written). Two honest references are available:

- **(T) the user's own corrections.** In all three correction sessions the user says
  the group whisper wrote as `5 2 0` is *"पाँच बार जीरो"* (five zeros): 103339 t9 (`5 बार 0`),
  131245 t15 (`5 बार 0`) / t17 (`0000`), 133627 t13–t15 (`5 को हटा … 5 जीरो लगा`). The
  lock §8 target `02690012000005203` was approved on that basis.
- **(C) self-consistency.** Two renderings of the same segment by the same speaker
  that differ prove at least one wrong, without knowing which.

Renderings of one number, one speaker, four sessions (`numeric_audit.py` §6):

| segment | renderings | result |
|---|---|---|
| head `026900` | `026900` ×4 (run), `026`+`9000` (131245: `9000` vs `900` in the same session's t11), `026`+`9, 0, 0, …`, digit words `जीरो टू सिस नाइन डबल जीरो` | 7/8 digit-exact; 1 contradiction; **1 no-observation** |
| middle `00000` (per T) | `520`, `5,2,0` ×2, `5,6,0,1`, `5,8,0,1`, `5,0,1` ×2, `5,2,0,1` | **zero-run rendered 0/8 times** in flowing dictation; rendered correctly only inside slow correction sentences (`5 बार 0`), and even then also as `0000` and `5 जीरो` |
| tail `5203`/`1203` | `5203` ×3 (103339, 133627), `1203` ×4 (125037, 131245) | cross-session contradiction, unresolvable from text |
| within-session tail pairs | 133627 t4 vs t12: 2 edits · 131245 t7 vs t11: 1 edit · 125037 t4 vs t6: 0 | 2 of 3 sessions contradict themselves |

Digit edit rate against (T): **25 edits over 84 reference digits ≈ 30 %** (n = 7
utterances; every error sits in the zero-run and the digit after it). Against the
weaker (C) alone: ≥ 3 of 8 tail renderings are provably wrong (≥ 1 digit each).
Whisper's `avg_logprob` does not separate them: correct `-0.25/-0.48`, wrong
`-0.20/-0.22/-0.43`, OOV no-observation `-0.13`.

Conclusion: **for this speaker and this dictation style (Hindi/English mixed, a
multiplier phrase inside a fast digit run), whisper-large-v3 batch text is not a
digit-perfect channel and offers no usable per-digit confidence.** The errors are
systematic (multiplier collapse: `4 बार 0 → 420`, `5 बार 0 → 5 2 0 / 5 x 0 / 5 8 0 1`),
not random. A lexicon patch per spelling (`सिस`, `पाइट`, `बट`, `x`) is what the code has
been doing for eight smokes; the table shows it cannot converge.

What this does **not** say: that STT must be replaced. It says a second, independent
observation of the digits is needed *whenever the first cannot be verified* — and
that today the chain cannot even express "unverified".

## 5. The missing boundary

The requested chain is

`Audio → VAD → STT → numeric observation → instruction understanding → operation →
proposal → confirmation → commit`

What exists (b228048):

```
Audio → VAD → STT text ──► is_echo(text)  [drops user replies that resemble the agent's line]
                        └─► precision_rail.decide(text)
                              ├ dictation_value(text)   regex slice of the STRING (or None)
                              ├ normalize_span(span)    words→digits, unknown words DROPPED
                              ├ Signals(text)           reject/confirm/restart/continue cues
                              ├ controller rows         operation chosen from text shape + cues
                              └ L1–L6                   proposal / delivery / commit  ✓ (safe)
```

**Missing boundary #1 — HEARD → UNDERSTOOD (a numeric observation object).**
Nothing between STT and the rail says *"digits [1,2,5,?,?,?,2,0,3], source=separated
list, tokens unknown=0, multiplier=none, confidence=none, endpoint=continued-within-
RESUME_WINDOW"*. Because that object does not exist:

- the append/replace decision reads the string's punctuation (§3 fact 1);
- an OOV token collapses to "no number here" instead of "a number with an unknown
  digit" (t17 — the only reason it did not commit the wrong value was L2's unheard flag);
- `5 जीरो` becomes `50` with no record that a count-word was consumed;
- t3/t4 arrive as two independent strings although the VAD already knows t4 resumed
  inside its window — the evidence is archived (`turn["premature_resume"]`) and read
  by L3 only, never by the dictation path;
- a correction's reference ("इसमें जो 5") cannot be bound to *the sequence the agent
  just read out*, because there is no sequence object to bind to, only the base string.

**Missing boundary #2 (found on the way, same class) — the echo filter sits *before*
the boundary and sees only text.** `main.is_echo` compares the romanized user turn to
the agent's last line with a 0.65 ratio, per-word window. Short Hindi confirmations
score as the agent's own words: `हाँ` is dropped after **35 of 46** rail lines, `ठीक है`
after 19/46, `सही है` after 17/46, `नहीं` after 19/46 (when spoken < 1.5 s after audio
end — exactly when a user answers a "confirm kar de?"). In 133627 t11 this ate the
only correct confirmation of the session. This is not a perception-of-digits problem
but it is the same missing distinction: the system cannot tell *user answered* from
*agent heard itself* without an acoustic/temporal channel; the corr score exists
(`echo_corr_score` 0.32 on t11 — low, i.e. *not* acoustically an echo) and is logged
as "shadow" only.

Everything the user experienced in 133627 after t4 is downstream of these two.
The rail rows (⑤) are where the symptoms *appear*; adding rows there would be
treating the string shape as if it were evidence.

## 6. What "uncertainty stops mutation" would require (design constraints, not a proposal)

Recorded so the next lock can start from facts; **nothing here is implemented.**

1. A **numeric observation** is a structured object: ordered digit slots (each `known
   digit | unknown | count-word-consumed`), the surface form, the token provenance,
   the endpoint evidence of the chunk, and — when available — a second opinion.
2. **UNDERSTOOD ≠ HEARD**: an observation with any unknown slot, an unresolved
   multiplier, or a contradicting sibling rendering is *not understandable*; the rail
   must be able to say so (a clarify that names the uncertain slot) instead of picking
   a row. Today the rail's only "uncertain" outcomes are `hold_edit`/`clarify` for
   *instructions*, none for *digits*.
3. **Operation from instruction, not from shape**: continuation cues (`आगे`, `इसके
   बाद`, `continue`), restart cues (`पूरा`, `फिर से`) and endpoint evidence decide
   append/replace; the digit list's punctuation must carry zero weight.
4. **References bind to the sequence under discussion**: "इसमें जो 5" resolves
   against the proposal that was just spoken, the base only when no proposal is open.
5. **Verification is a first-class state**: a value is *verified* only when the
   user confirmed a spoken rendering of it (L2 already gives this) — and the echo
   filter must not be able to eat that confirmation (acoustic corr + timing, not text).
6. **Second observation**: where the digit channel is known-weak (multiplier phrases,
   fast runs, OOV digit words) a second recognizer pass or a constrained re-ask per
   group is the only way to *raise* certainty; text-side patches can only *hide* it.
   This is the point at which a "feeder"/secondary recognizer belongs — after the
   observation object exists, not before.

## 7. Answer

**Why can the agent still fail to know the number?** Because the only thing it ever
"knows" is a whisper string. L1–L6 guarantee that string cannot silently become the
stored value; they cannot make the string true, cannot express that it might be false,
and cannot stop a *different* string (a confirm word, a comma layout, an OOV token)
from deciding what operation is performed on it. In 133627 the stored value was
protected on every turn, and the user still left without the agent holding
`02690012000005203` — because the correct sequence was never *observed* as a whole
(the zero-run was never transcribed in flowing speech), the one correct head
confirmation was eaten before the rail, and every correct partial was interpreted by
its punctuation.

**First missing boundary:** HEARD → UNDERSTOOD — a numeric observation with explicit
uncertainty, produced from STT + endpoint evidence *before* any operation is chosen.
Second, same class: the echo/turn-validity gate must not decide on text similarity
alone.

**On STT:** insufficient *as the sole channel* for this dictation style (≈30 % digit
edit rate against the user's own corrections; multiplier phrases collapse 8/8 times in
flowing speech; no per-digit confidence). Replacement is not the conclusion; an
observation layer that can hold "unknown" and ask for — or fetch — a second look is.
